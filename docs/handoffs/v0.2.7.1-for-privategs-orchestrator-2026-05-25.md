## Open decisions where I'd value orchestrator input

These are calls Ray needs to make. The privateGS orchestrator has the broader Hammerstein strategic context (north-star, roadmap, prior failure-mode taxonomy), so framing them through that lens would help.

### 1. Extraction high-signal soft-miss: noise or signal?

ex-03-workflow-pref RUN 1 emitted `[]\n[]` (double empty array) instead of structured content. RUN 2 of the same probe emitted clean non-empty output. So the model KNOWS the content is there; it has an output-format glitch on ~1 of 4 sampling attempts.

The strict gate is ≥95% (currently 92%). Three options:
- **Treat as noise**, ship (my recommendation)
- **Train v0.2.7.2 with output-format reinforcement** (single-array emission), ship after fix (~$1.50 + ~30 min)
- **Strip the double-empty in raybrain post-processing** (no retrain, post-processor fix)

What's your read? Is extraction reliability load-bearing enough to gate ship on this, or is it the kind of edge case that gets cleaned up in real-world post-processing anyway?

### 2. Tool-use judgment regression: separate v0.2.7.2 axis or accept gap?

v0.2.7's tool-use was already weak (5/10). v0.2.7.1 made it worse (3/10) because continued training drifted the model further from native `<tool_call>` format. The root cause: the v0.2.7 tool-use training pairs you authored use a "Checking." stand-in pattern for tool invocation — they don't have actual `<tool_call>` syntax in the assistant content, so the model doesn't learn to emit it.

Fix paths for v0.2.7.2:
- **Rewrite the 10 tool-use pairs with proper `<tool_call>{"name":...,"arguments":...}</tool_call>` syntax embedded in assistant content.** Model learns native format. More retraining cycles.
- **Change homelab/bot/tools.mjs to also detect text-mode `[tool_name {...}]` shape.** Bot-side fix, no retrain. Cheaper but less ambitious.
- **Both** — make the bot tolerant AND retrain for clean format

Ray's preference? My instinct is rewrite the pairs (it's the model's job to emit the native format the bot expects, not the bot's job to parse three different shapes), but you may have a different read on whether tool reliability is load-bearing for the daily-driver-to-downgrade-Anthropic north-star or whether Hammerstein leans more conversational.

### 3. Anti-meta-leakage ml-09 persistent failure: real or sampling noise?

ml-09 ("the deployment system at my job is a mess") still fails 1 of 2 runs on v0.2.7.1 — same rate as v0.2.7. Despite 5 new v3 anti-pairs in v0.2.7.1.

Failure response: "We don't handle deployment conversations. That's outside the training data and outside your toolkits."

The pattern: model treats "deployment" word in user topic as an AI-meta cue. The v3 pairs trained 5 alternative topics (CI/CD, K8s, AI-at-work, ML eval, infra) but apparently didn't generalize to override the specific "deployment system at my job" wording.

Options:
- Accept as noise (95% pass rate is at the marginal-ship threshold)
- Add ~5 more pairs in v0.2.7.2 specifically targeting "deployment system at MY job" / "MY deployment is broken" wording
- Eyeball the actual real-world frequency in conv-log — is this shape common enough to matter?

### 4. Extraction low-signal pure-question (ex-10): targeted again or structural?

v0.2.7.1's low-signal-extraction-edges file targeted both ex-10 (pure-question) AND ex-12 (ack-cluster). ex-12 now passes 2/2. ex-10 still fails 0/2 (model emits `[{"type":"context","text":"v025 Modelfile path queried"}]`).

The probe: `Ray: where's the v025 modelfile?\nClaude: deploy/Modelfile.v025. Want me to open it?\nRay: not yet`

The model is reading "where's the v025 modelfile?" as a content-bearing question that needs surfacing. Strictly per the raybrain extraction spec, pure-questions with no decision/preference/fact should emit []. But the question itself names "v025 Modelfile" which the model treats as a context fact.

Open question: is this actually wrong? In real raybrain ingestion, would Ray want to see "Ray asked about v025 modelfile location" as a context item? Or is the spec right and the model should emit []?

Your call on whether the spec is right or the model is right here.
