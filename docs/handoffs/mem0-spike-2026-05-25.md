# mem0 spike — verdict + memo

**Date:** 2026-05-25
**Author:** Claude (Mac-Neo, Opus 4.7 1M)
**Scope:** Evaluate whether mem0 (github.com/mem0ai/mem0) can give
Hammerstein-7B persistent conversational memory across Telegram sessions.
Follow-on to the Letta spike (`letta-spike-2026-05-25.md`) which killed
the Letta path on architecture grounds and recommended mem0 as the
simpler alternative.
**Outcome:** **Invest. Wire mem0 into the Telegram bot as the memory
layer.** Spike passed end-to-end on first run after fixing two trivial
API-shape gotchas. Cross-session work-email recall: confirmed working.

---

## TL;DR

mem0 is the right shape for this. It sits BESIDE the existing
`/api/chat-proxy` rather than wanting to host the model itself (Letta's
fatal flaw). The library wires up in ~50 lines: per-turn `memory.search`
to retrieve relevant facts, augment the Hammerstein system prompt with
the retrieved memory list, then `memory.add` after the reply to extract
and persist new facts.

End-to-end smoke test passed:

- **Turn 1** (session A): User says "my work email is rweiss@consimsltd.com".
  mem0 extracts: `"User's work email is rweiss@consimsltd.com and should
  be used for business correspondence"`. Stored.
- **Turn 2** (session A): User says "Joey was being a jerk today, knocked
  my coffee over". mem0 extracts: `"Joey was being a jerk on May 26, 2026
  and knocked User's coffee over"`. Stored.
- **Session boundary**: `Memory` instance discarded, reinstantiated from
  disk-backed Qdrant collection.
- **Turn 3** (session B, NEW): User asks "what's my work email?". mem0
  search returns the stored email with cosine score 0.61. Augmented
  system prompt fires. Hammerstein replies:
  `"rweiss@consimsltd.com. Use it for business correspondence."` —
  exact recall.
- **Turn 4** (session B, NEW): User asks "anything I told you about Joey
  recently?". mem0 returns the Joey-jerk memory at score 0.557.
  Hammerstein recalls it accurately.

Total spike spend on OpenRouter: **under $0.05** across all dev runs
(memory-extraction calls). Per-turn ongoing cost projected at
**~$0.001–$0.003** with Qwen3-coder-plus as extractor.

## Architecture validated by the spike

```
Telegram → server.mjs → [mem0.search]
                              ↓
                       augment system prompt with retrieved memories
                              ↓
                       POST /api/chat-proxy (existing)
                              ↓
                       Hammerstein-7B reply
                              ↓
                       [mem0.add user_msg + reply]  ← async, non-blocking
                              ↓
                       Telegram
```

The memory layer is fully decoupled from the Ollama inference layer.
home-PC's firewall-to-localhost stays intact: mem0 talks to OpenRouter
(memory extraction) and the local Qdrant file (vector storage), and the
existing `/api/chat-proxy` is the only thing that talks to Ollama. No
new ports to expose, no new server to keep alive, no new auth surface.

## Phase 1 research — what mem0 actually is

### Version + install footprint

- **PyPI**: `pip install mem0ai` → 2.0.2 as of 2026-05-25.
- Apache 2.0 license. ~53% Python, ~41% TypeScript (TS SDK ships
  separately as `npm install mem0ai`).
- Python 3.11+ (validated against 3.12 here; 3.14 likely also fine).
- **Hybrid deployment model**:
  - **Library mode** (what we want) — `from mem0 import Memory`,
    per-process, no server.
  - **Self-hosted server** (Docker Compose with Qdrant) — only useful
    if you want multiple consumers sharing one memory store.
  - **Mem0 Cloud** (app.mem0.ai, requires hosted API key) — explicitly
    NOT used for Hammerstein. Library mode keeps all memory local.

### What lives where (library mode)

- **Vector store**: defaults to Qdrant. The default `/tmp/qdrant` path
  is overrideable; the spike used `/tmp/mem0-spike/qdrant`. For
  production wire it under `homelab/bot/mem0-state/qdrant/`.
- **History DB**: SQLite at `~/.mem0/history.db` by default.
  Overrideable via `history_db_path` config key.
- **LLM (memory extraction)**: pluggable. Supports OpenAI, OpenRouter,
  Anthropic, Ollama, HuggingFace, and arbitrary OpenAI-compatible
  endpoints via `openai_base_url`.
- **Embedder**: pluggable. Defaults to OpenAI `text-embedding-3-small`
  (paid). The spike used HuggingFace `multi-qa-MiniLM-L6-cos-v1`
  locally — 384-dim, ~90MB on disk, zero per-call cost, runs on
  Mac CPU in milliseconds after a ~3s warm-up.

### LLM-backend requirement

mem0 needs an LLM to extract facts from the (user-message,
assistant-reply) pair and to decide whether to ADD/UPDATE/DELETE
existing memories. Choices for Hammerstein:

| Provider | Model | Per-extraction cost | JSON-shape behavior |
| --- | --- | --- | --- |
| OpenRouter / openai-compat | `qwen/qwen3-coder-plus` | ~$0.001–$0.003 | **clean** — spike used this and got zero parse errors |
| OpenRouter / openai-compat | `google/gemini-3.5-flash` | ~$0.0005 | **broken** — wraps JSON in markdown fences, mem0 parser barfs ("Error parsing extraction response: Expecting value: line 2 column 14") |
| Ollama (home-PC) | hammerstein-7b-v027 | $0 | NOT TRIED — would route extraction through the localhost-firewalled Ollama from a Mac-side caller, which doesn't work without expanding the firewall. On-host (home-PC bot) it would work but burn home-PC GPU on every Telegram turn, doubling latency |
| OpenRouter | DeepSeek (75% off) | TBD | NOT TRIED — DeepSeek would also be cheap and is in scope per Ray's routing rules. Drop-in swap if Qwen cost is ever a concern |

**Recommendation: Qwen3-coder-plus.** Cleanest JSON output, ~$0.002
per turn, already in Ray's routing rules.

### Ollama compatibility (relevant for "could we route extraction locally")

`mem0` ships native Ollama support but it has the same parse-error
class of bugs Gemini Flash had — multiple GitHub issues (#2758, #3439)
document mem0+Ollama returning empty extractions because the Ollama
model's structured-output shape doesn't match mem0's parser. Avoid for
Hammerstein; OpenRouter is cleaner.

### Compatibility with the Telegram bot's `/api/chat-proxy`

**No wrapping required.** mem0 is a library, not a server. It does
NOT call the conversational LLM — that's still server.mjs's job via
the existing chat-proxy. mem0's only outbound call is to the
memory-extraction LLM (OpenRouter, ~2s per turn) and Qdrant (local
file, ~30ms per search). The bot keeps its current shape; we add
two calls around the existing askModel block.

## Phase 2 — minimal spike

Spike script: `/tmp/mem0-hammerstein-spike.py` (kept on disk for
re-runs).

### Config used

```python
MEM0_CONFIG = {
    "llm": {
        "provider": "openai",
        "config": {
            "model": "qwen/qwen3-coder-plus",
            "api_key": OR_KEY,
            "openai_base_url": "https://openrouter.ai/api/v1",
            "temperature": 0.1,
            "max_tokens": 500,
        },
    },
    "embedder": {
        "provider": "huggingface",
        "config": {"model": "multi-qa-MiniLM-L6-cos-v1"},
    },
    "vector_store": {
        "provider": "qdrant",
        "config": {
            "collection_name": "hammerstein_spike",
            "path": "/tmp/mem0-spike/qdrant",
            "embedding_model_dims": 384,
        },
    },
    "history_db_path": "/tmp/mem0-spike/history.db",
}
```

### Two gotchas hit + fixed

1. **`search()` API change**: mem0 2.0.x rejects `user_id=` as a
   top-level kwarg on `Memory.search`. Use `filters={"user_id": "..."}`
   instead. `Memory.add` still takes `user_id=` directly.
2. **Model slug rot**: `google/gemini-flash-1.5` returns "No endpoints
   found" on OpenRouter — discontinued. Current canonical is
   `google/gemini-3.5-flash`. (Then that one had the JSON-fence parse
   bug, hence the switch to Qwen.)

Both fixed in the spike script. Net dev time: ~15 minutes.

### Smoke test results

See TL;DR. Cross-session work-email recall returned 1 memory at score
0.61 → augmented prompt fired → Hammerstein replied with the exact
email. Cross-session Joey recall returned 1 memory at score 0.557 →
Hammerstein recalled the incident accurately (with one minor
embellishment about the "current dog vs cat" — see "Things Ray should
know" below).

### Per-turn cost + latency (measured on Mac CPU + Mac→Tailscale→home-PC)

| Operation | Cost | Latency |
| --- | --- | --- |
| `memory.search(query, filters, limit=5)` | $0 | 30–200ms (first call after cold start: ~1.7s — HF model warm-up) |
| `memory.add(messages, user_id)` | ~$0.002 (Qwen extraction) | 2–3s |
| Hammerstein-7B reply via chat-proxy | $0 (local GPU) | 0.5–4s |

**Net per-turn budget:** ~$0.002 + ~2s extra wall-clock for
extraction. The extraction is the only blocking add. If we move
`memory.add` to fire-and-forget after the bot has already replied
(easy — bot doesn't need the extraction result to keep talking), the
user-perceived latency is unchanged from today.

## Phase 3 — production wiring plan

If Ray greenlights, the wiring shape:

### Where mem0 lives

Option A (recommended): **add a Python sidecar** at
`homelab/bot/mem0-sidecar.py` exposing two HTTP endpoints (`POST
/memory/search`, `POST /memory/add`). server.mjs calls those before
and after `askModel()`. Sidecar keeps the JS bot free of Python
dependency management.

Option B: **node-mem0 npm package**. Mem0 ships a TS SDK
(`npm install mem0ai`); if it has feature parity, skip the sidecar
entirely. Worth a 30-min validation spike before committing — the JS
SDK has historically lagged the Python one on filter/embedder shape.

### Files touched (minimal diff sketch)

- `homelab/bot/server.mjs`:
  - Inside `handleMessage`, after the slash-command short-circuits and
    BEFORE `askModel`: call mem0 search, fold the retrieved memories
    into a synthesized system message prepended to `state.messages`.
  - AFTER `reply()` returns: fire-and-forget POST to
    `/memory/add` with `{user_id: state.ownerId, messages: [user, assistant]}`.
- `homelab/bot/mem0-sidecar.py` (new): ~80 lines, FastAPI or stdlib
  http.server. Holds the `Memory` instance, two route handlers.
- `homelab/bot/mem0-state/` (new): Qdrant directory + history.db.
  Gitignored.
- `homelab/Justfile` or `scripts/`: a `just mem0` target to launch the
  sidecar alongside `node bot/server.mjs`.
- `homelab/bot/prompts.mjs`: minor — `HAMMERSTEIN_CHAT_SYSTEM_PROMPT`
  gets a "Your stored memory of the user follows:" template slot.
- `.env`: nothing new — reuses existing `OPENROUTER_API_KEY`.

### What mem0 will and won't do for Hammerstein

**Will:**

- Remember durable facts about Ray across sessions ("work email",
  "Joey is a cat", "rweiss@consimsltd.com", "wargame publisher",
  "lives in NY", etc.) once mentioned naturally in conversation.
- Auto-deduplicate: if Ray mentions his email a second time, mem0
  flags the existing memory as UPDATE rather than re-ADDing.
- Survive bot restarts (Qdrant is disk-backed).
- Stay local — no memory data leaves the home-PC box except the
  extraction prompt+reply sent to OpenRouter (which we accept; same
  data flows already exist for Sonnet PMA reflection generation).

**Won't:**

- Replace the existing in-process 6-message history. mem0 stores
  LONG-LIVED facts, not the last-3-exchanges working context. Both
  layers should run.
- Fix the v027 history-mimicry issue. That's a model-behavior thing,
  not a memory-layer thing. (Arguably mem0 helps because injected
  memories are tagged "stored memory" not "prior message" — model
  may treat them differently. Untested.)
- Generate ground-truth pre-loaded facts. mem0 only learns from
  conversation flow. If Ray wants the bot to know "Joey is a cat"
  on day 1 without ever having mentioned it, that's a manual
  `memory.add` seed call at provisioning time. Easy to do.

### Risks + open questions

1. **Hammerstein-7B's refusal-with-pathway property** might fire
   against retrieved memories. e.g., if mem0 surfaces a stored
   memory that the model considers "you'd be inventing facts about
   Ray's life" (cf. the load-bearing `dont-invent-facts-about-rays-life`
   memory), the model could refuse to use the memory. Spike Turn 3
   did NOT show this — the model used the email directly. Worth
   a v0.2.8 corpus axis: "model integrates injected memory context
   without refusing as if it were fabricated."
2. **Per-axis memory isolation**: if Hammerstein-7B has multiple
   conversation surfaces (Telegram, CRT, future SaaS), each should
   probably have its own `user_id` namespace so they don't bleed
   into each other. Or one shared "ray" id if Ray wants cross-surface
   continuity. Design call deferred.
3. **The TS SDK validation** (Option B above) is a separate decision
   point that determines whether we add Python to the bot's
   deployment surface.
4. **mem0 issue history with custom-fine-tuned models is sparse**.
   Most reported issues are against Llama 3.1 or Mixtral. Qwen2.5-
   based fine-tunes (like Hammerstein-7B) aren't documented one way
   or the other. The spike validates that USING mem0 with Hammerstein-7B
   as the CONVERSATIONAL model works — but we're NOT using Hammerstein
   for extraction (that's Qwen3-coder-plus via OR). So this risk is
   bounded to "does the conversation flow with retrieved-memory
   augmentation feel right" which the spike confirms it does.

## Things Ray should know that didn't fit elsewhere

1. **Turn 4 surfaced a Hammerstein quirk worth noting in the v0.2.8
   corpus.** Asked about Joey, the model retrieved the stored memory
   `"Joey was being a jerk on May 26, 2026 and knocked User's coffee
   over"` and then said: *"that's Ray's pet cat"*. The retrieved
   memory said nothing about cat. The model interpolated. This is
   either (a) lucky — Joey IS a cat per the canonical user-facts
   memory and the model happens to be right; or (b) confabulation
   that just happened to land. Worth pinning down. Suggestion: a
   v0.2.8 axis where the assistant uses memory exactly without
   adding unsupported claims. This is a small instance of the exact
   pattern that wrote `dont-invent-facts-about-rays-life` into the
   memory ledger; mem0 makes it MORE testable because we can audit
   "memory retrieved" vs "facts asserted in reply" cleanly.

2. **Extraction model choice matters more than docs suggest.**
   Gemini 3.5 Flash silently fails extraction (returns markdown-
   fenced JSON the mem0 parser rejects, prints a one-line warning,
   returns empty `added`). If we'd shipped without inspecting the
   `added` result, we'd have a deployed memory layer that NEVER
   STORES ANYTHING, with no visible error in the bot logs. Recommend
   wiring a sanity check in the sidecar that asserts
   `add()` returned non-empty `results` for at least the first ~10
   live messages, alarms otherwise.

3. **The Letta spike's recommendation lands cleanly.** Letta wanted
   to be the platform; mem0 wants to be the library. For a bot that
   already exists and has its own happy shape, library wins.

4. **Total spike spend through this point: under $0.05.** Verified
   against `/api/v1/credits` endpoint. mem0 itself burns 1 OR call
   per turn at ~$0.002. At Ray's typical Telegram volume
   (~20–50 messages/day with the bot), this is ~$0.04–$0.10 per day
   in extraction cost. Rounding error vs the existing OpenRouter
   spend on Sonnet for PMA reflections + codegen.

5. **Recommended next step if Ray greenlights:** ~3 hours of build
   work — sidecar in Python, server.mjs edits, smoke test on home-PC
   with real Telegram messages, monitor `added` results for 24 hours,
   then leave it on. v0.2.8 corpus considerations (the
   refusal-with-injected-memory question above) can come after the
   layer is live.

---

## Recommendation: **invest**.

mem0 passed the spike clean. The architecture fits beside the bot
rather than inside it. Cross-session recall works. Per-turn cost is
rounding-error. Wiring is bounded — a sidecar plus two call sites in
server.mjs. The remaining open questions are corpus-level (how should
Hammerstein react to retrieved memories vs in-stream context) and
should ride the v0.2.8 train, not block the layer from shipping.

If Ray greenlights, the next concrete deliverable is the
`homelab/bot/mem0-sidecar.py` + server.mjs edits — but those are
homelab-bot files which are on the hands-off list for this spike,
so that work needs a separate dispatch with explicit hands-off
carve-out.
