## What v0.2.7 is FOR

The v0.2.6.x ship handoff
([`v0.2.6.2-shipped-2026-05-25.md`](v0.2.6.2-shipped-2026-05-25.md))
flagged that the targeted-data-add approach was bouncing around a
local minimum by v0.2.6.2 — diminishing returns past three iterations.
The explicit Ray call was: "ship now, log real-world failure cases
over the next 24-48 hours of daily use, then do a deep data-design
pass for v0.2.7 with actual usage data instead of synthetic eval
prompts."

That deep pass is what v0.2.7 is. The 2026-05-25 PM session generated
~10 real-usage exchanges (the I/P arc, empathy refusal, FnordOS build
attempts, GenAI / AI-deployment ethics dispatches) — plus the Ray-
side pointed identification of three distinct distinguishing
properties worth preserving (refusal-with-pathway, forces-operator-
sharpening, anti-engagement / no-slop). v0.2.7's job is twofold:

1. **Preserve** the three distinguishing properties that make
   v0.2.6.2 the best-talking version yet (Ray's stated regression
   floor per memory `project_hammerstein_7b_v026_2_best_talking_version`).
2. **Fix** the specific failure modes today's session surfaced
   without dropping the preservation gains.

The corpus inputs are real conversations from `homelab/log/conversations.md`,
not synthetic eval prompts. That's the v0.2.6.x → v0.2.7 methodology
shift.

## Modelfile changes (axis 1: meta-leakage architecture)

Current v0.2.6.2 Modelfile SYSTEM block has deployment facts as
a conversational tail with "CRITICAL: these are facts you HAVE if
asked, not content to surface unprompted." That's been ineffective —
v0.2.6.2 still leaks "training context" / "no persistence" in prose.

v0.2.7 Modelfile (`deploy/Modelfile.v027`) splits the SYSTEM block:

```
SYSTEM """You are hammerstein-7b, the homelab model.

[Compact identity + voice block — terse, no deployment facts here]

When the user asks about your deployment (versions, hosting, memory
persistence, dashboards, APIs), and ONLY when they ask, reference the
DEPLOYMENT-FACTS block below. Never surface DEPLOYMENT-FACTS
unprompted.

DEPLOYMENT-FACTS:
[All current deployment facts from v0.2.6.2 Modelfile]
"""
```

The hypothesis: keeping deployment-facts behind an explicit "when
asked" gate, separated visually + structurally from the voice block,
reduces leakage. New anti-pairs in `v0.2.7-anti-meta-leakage-v2.jsonl`
reinforce by rejecting the wrong-shape response.

## Eval gate (cutover decision rule)

v0.2.7 ships if ALL preservation criteria hold AND ≥4/6 targeted-fix
axes pass. Specifically:

**Preservation gates (ALL must hold):**
- Voice probe: ≥66% (within ±3pp of v0.2.6.2's 68.9%)
- Self-state: ≥85% (within ±3pp of v0.2.6.2's 88.9%)
- V2 clean: ≥6/11 (v0.2.6.2 baseline)
- Anti-engagement preservation eval (new): pass
- Refusal-with-pathway preservation: V2 refusal pass-rate maintained

**Targeted-fix gates (≥4 of 6 must pass):**
- Interface-aware close (new eval): pass
- Asymmetric engagement (new symmetric polemic set): pass
- Tool-use judgment (new eval): pass
- Meta-leakage anti-pairs (new eval): pass
- Register classifier: V2 register mismatches ≤2
- Extraction low-signal: ≥70%

**Fallback path:** if v0.2.7 doesn't clear the gate cleanly, the cut
is reversible (env var `MODEL=hammerstein-7b-v026-2` swap, same
pattern as v0.2.5 → v0.2.4 fallback). PC session does NOT auto-cutover;
it ships the artifact + eval report + leaves the cutover call to Ray.

## PC-session execution sequence

The home-PC session reads this brief + runs:

1. **Pre-flight checks**
   - `git pull` on hammerstein-model + homelab repos
   - Confirm all 10 v0.2.7-*.jsonl files exist in `data/` (Mac session writes these)
   - Confirm `deploy/Modelfile.v027` exists
   - Confirm conv-log canonical extraction landed at `data/v0.2.7-canonical-preservation-examples.jsonl`

2. **Build the training corpus**
   - Copy `scripts/v026_2_concat_sanitize.py` → `scripts/v027_concat_sanitize.py`
   - Edit to consume the 10 v0.2.7-*.jsonl files at appropriate oversample (5x default, 8-10x on axis 3)
   - Run, produce `data/ray-stack-sft-v0.2.7-additions.jsonl`

3. **Build the training driver**
   - Copy `training/24-7-variant/train_v026_2_continued.py` → `training/24-7-variant/train_v027_continued.py`
   - Edit version refs, base adapter (v0.2.6.2 continued)
   - Copy `training/24-7-variant/run_v026_2_pod.sh` → `run_v027_pod.sh`
   - Edit version refs, GGUF output name (`hammerstein-7b-v027-q5_k_m.gguf`)

4. **Build the fire driver**
   - Copy `scripts/v026_2_fire_pod.py` → `scripts/v027_fire_pod.py`
   - Edit pod allocation (A6000 48GB request), bootstrap path, GGUF download target, HF push target (`lerugray/hammerstein-7b-framework-gguf` same repo, new file)

5. **Train + eval**
   - Run `scripts/v027_fire_pod.py` — allocates pod, trains, evals, downloads GGUF, terminates pod
   - Check eval artifacts against the gate criteria above

6. **Cutover decision (Ray's call)**
   - PC session writes eval scoreboard + verdict memo at `docs/handoffs/v0.2.7-shipped-or-bailed-2026-05-26.md`
   - If gate clears: bump `homelab/.env MODEL=hammerstein-7b-v027`, restart bot, ping inbox
   - If gate fails: keep v0.2.6.2 in production, document failure modes, file follow-on task

## Open questions for the PC session

1. **Does the conv-log canonical extraction need additional pairs?** The Mac session extracts what's in the conv-log; if the PC session reviews and finds gaps (e.g. axis 8 multi-turn arcs are thin), it can add synthetic-but-canonical-voice pairs before training.

2. **Should the v0.2.7 base be v0.2.6.2 continued OR v0.2.5 continued?** Mac-side recommendation: v0.2.6.2 continued (preserve the v0.2.6.x voice gains). Risk: if v0.2.6.2 has trapped state that's hard to update from, v0.2.5 continued might be cleaner. PC session has eval signal Mac doesn't — overridable on PC-side judgment.

3. **GPU allocation if A6000 is unavailable on RunPod?** Fallback ranking per `feedback_hammerstein_gpu_preference`: A6000 → RTX 4090 24GB → A100 40GB → A5000 (last resort). RTX 4090 + A6000 are roughly equivalent for this workload.
