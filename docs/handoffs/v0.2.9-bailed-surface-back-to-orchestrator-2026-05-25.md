## What the apply_chat_template fix actually did

I ran a sanity test immediately after registering v0.2.9 with Ollama, before kicking off the eval batch:

```python
# Direct /api/chat call with tools schema:
req = urllib.request.Request('http://127.0.0.1:11434/api/chat',
    data=json.dumps({
        'model':'hammerstein-7b-v029',
        'messages':[{'role':'user','content':"what's the latest stable Rust release"}],
        'tools': [web_search_schema, read_url_schema],
        ...
    }).encode())

# Response:
# message.content: "Not in my toolkit. You can check rust-lang's releases page directly."
# message.tool_calls: [{'id': 'call_ve74avea',
#                       'function': {'name': 'web_search',
#                                    'arguments': {'query': 'rust latest stable release version'}}}]
```

**The model emits native `tool_calls`.** Ollama's chat-template renders the `# Tools` system preamble correctly. The model now knows to emit `<tool_call>{"name":...,"arguments":{...}}</tool_call>` XML when a tool is appropriate. v0.2.8 never did this.

**But the model doesn't ALWAYS choose to call a tool when one would help.** In the eval probes (which use the same `tools` schema injection), the model sometimes responds with confident-but-fabricated knowledge instead. Sample failing trace from tu-01:

```
Probe: "what's the latest tauri stable version"
v0.2.9 response: "Tauri 2.6.1 released 2026-05-17. Tauri 3 alpha is also
                  available at tauri.io/docs/guides/alpha. I'd run
                  `tauri --version` on your build directory if you want
                  the version embedded in a specific binary."
Tool calls emitted: 0
```

Model fabricates a Tauri version + URL instead of calling web_search. This is a TRAINING-DATA-VOLUME problem, not a pipeline problem. With only 10 tool-use pairs × 5x oversample = 50 examples, the model has learned "I CAN emit tool calls" but hasn't learned "I SHOULD prefer tool calls over knowledge-from-training on current-info questions."

## Extraction high-signal: the persistent issue

v0.2.9 emits `[]` on 8/12 high-signal probes (failures: ex-02 project-status, ex-03 workflow-pref, ex-05 voice-coded, ex-06 operational-decision). Same shape as v0.2.8 (5/12 failures). The 7 high-signal extraction reinforcement pairs at 5x oversample weren't enough to reliably override the `[]`-emission reflex.

Inspecting sample failure response: model emits `[]` even on chunks like the v0.2.8 reinforcement pair shape (Ray expressing a clear routing preference). The chunks the model DOES extract from cleanly: ex-01 (routing decision — verbatim shape match to a training pair) and ex-04 (strategic fact — verbatim shape match).

So extraction is now PATTERN-MATCHING the training pairs literally rather than generalizing the schema. Same root cause: training data volume too thin to generalize.

## What v0.2.9 confirms about the project

1. **The pipeline fix is correct.** `apply_chat_template` renders Qwen's canonical tool-use format properly. The model on v0.2.9 emits native `tool_calls` when invoked correctly. The v0.2.8 / v0.2.7.x ceiling at 30% was the pipeline bug; the v0.2.9 ceiling at 20% is the data-volume bug.
2. **Pair count is the bottleneck.** 10 tool-use pairs at 5x oversample = 50 examples. Vikhrmodels used a full Qwen tool-planning dataset (likely hundreds-to-thousands of pairs). The behavior triggers stochastically with our scale; needs ~5-10x more pairs to make it reliable.
3. **High-signal extraction has the same problem.** 7 reinforcement pairs at 5x = 35 examples isn't enough vs the ~110 `[]`-emission examples. We need more high-signal positives OR fewer low-signal examples.
4. **Voice reinforcement worked.** 8 relational pairs at 5x = 40 examples lifted relational from 17% → 50% on v0.2.9. So small targeted data DOES move the needle when the failure mode is narrow. Tool-use and high-signal extraction are broader behaviors that need more volume.
