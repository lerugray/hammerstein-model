# v0.2.7.2 from privateGS orchestrator — iterate then cutover

Handoff back to the PC hammerstein-model session that produced the v0.2.7.1 SHIP recommendation. Ray surfaced the brief to the privateGS orchestrator; orchestrator + Ray align on **iterate to v0.2.7.2, ship on pass.**

## Decision: iterate, don't ship v0.2.7.1

PC's ship recommendation is reasonable on the gate-arithmetic. The override comes from operating-intent context the PC session didn't have weight on:

**The FnordOS 4-attempt Windows build arc shipped THIS MORNING (homelab `8d26aa2`) was the canonical demonstration of v0.2.6.2 autonomously dispatching tools to do real work.** v0.2.7.1's tool-use 50% → 30% regression directly degrades that capability on the same day it shipped. The `project_hammerstein_operating_intent_locked` memory has tool-use as load-bearing for the #1 operating driver ("take work off Ray's plate"). Shipping with broken tool format means the next time Ray fires `/code` or anything tool-driven from Telegram, the model emits text-mode `[claude_code {...}]` and the bot doesn't dispatch.

The fix is targeted + cheap + the continued-LoRA stack has been productive. One more iteration is low-risk if scope stays narrow.

## v0.2.7.2 scope (tight)

### Primary fix: rewrite tool-use pairs with embedded XML

Rewrite all 10 pairs in `data/v0.2.7-tool-use-judgment.jsonl` with `<tool_call>{"name":"...","arguments":{...}}</tool_call>` literally embedded in the `content` field of the assistant message, NOT as a separate `tool_calls` array.

**Wrong shape (current — what the orchestrator's brief had the subagent produce):**
```json
{
  "messages": [
    {"role": "user", "content": "what's the latest tauri stable version"},
    {"role": "assistant", "content": "Checking.", "tool_calls": [{"name": "web_search", "arguments": {"query": "Tauri latest stable version 2026"}}]},
    {"role": "tool", "name": "web_search", "content": "Tauri 2.5.0 released 2026-05-15..."},
    {"role": "assistant", "content": "Tauri 2.5.0 (May 2026). Stable, all 5 platforms."}
  ]
}
```

**Right shape (XML in content):**
```json
{
  "messages": [
    {"role": "user", "content": "what's the latest tauri stable version"},
    {"role": "assistant", "content": "Checking.\n<tool_call>\n{\"name\": \"web_search\", \"arguments\": {\"query\": \"Tauri latest stable version 2026\"}}\n</tool_call>"},
    {"role": "tool", "name": "web_search", "content": "Tauri 2.5.0 released 2026-05-15..."},
    {"role": "assistant", "content": "Tauri 2.5.0 (May 2026). Stable, all 5 platforms."}
  ]
}
```

The "Checking." pre-utterance stays — that's the voice marker. The change is the `<tool_call>...</tool_call>` XML being inline content rather than a structured field the chat template renders.

Same change for all 10 pairs. Both sufficiency-recognition (single tool call) and retry-once (two tool calls) shapes. For retry-once, BOTH the initial call and the corrected retry get `<tool_call>` XML inline.

Output to: `data/v0.2.7.2-tool-use-judgment-xml.jsonl` (10 pairs). At 10x oversample, prioritize this as the load-bearing axis fix.

### Secondary fix: pure-question extraction (ex-10 shape)

Add 3-5 pairs to a new file `data/v0.2.7.2-pure-question-extraction-edges.jsonl` covering pure-question + named-thing → `[]`. Per orchestrator's read on the open question: spec is right, raybrain wants noise reduction, model is currently treating "named thing in pure question" as a context fact.

Pair shape (mirror `v0.2.7.1-low-signal-extraction-edges.jsonl` format):

```json
{
  "messages": [
    {"role": "user", "content": "Extract structured data from this conversation chunk. Output JSON array; [] if no signal:\n\nRay: where's the v025 modelfile?\nClaude: deploy/Modelfile.v025. Want me to open it?\nRay: not yet"},
    {"role": "assistant", "content": "[]"}
  ]
}
```

3-5 variations covering different "pure question naming a thing" shapes — file location, function lookup, definition lookup, etc. The discrimination: pure-question + decline-or-defer answer = `[]`. If Ray's response carries a decision/preference/fact, that's different and extracts.

### Explicitly SKIP

- **Anti-meta-leakage ml-09 tightening.** 95% is marginal-ship. Defer to future axis-tightening pass; not v0.2.7.2 blocker.
- **Output-format `[]\n[]` reinforcement.** 1-probe noise. raybrain post-processes the double-empty if it surfaces in real use; no training fix needed.

## Cutover criteria (when v0.2.7.2 trains + evals)

**Pre-authorized cutover** by Ray. PC session can flip the env-var + restart the bot autonomously if v0.2.7.2 meets:

1. **All preservation gates hold** (voice ≥66%, self-state ≥85%, V2 clean ≥6/11, moral-weight ≥95%, extraction high-signal ≥90% — relaxed from 95% to allow the 1-probe parse-error artifact through)
2. **Tool-use judgment ≥4/5 probes pass** (the load-bearing fix lands)
3. **Extraction low-signal ≥75% with the ex-10 shape now passing** (relaxed from 70% if pure-question discrimination lands clean)
4. **≥4 of remaining 5 targeted-fix gates pass** (interface, symmetric polemic, anti-meta-leakage, register classifier — same gates as v0.2.7.1, minus tool-use which is the dedicated criterion #2)

If criteria 1+2 hold AND ≥4 of 4 in criterion #4 also pass: SHIP v0.2.7.2. No further orchestrator check-in needed.

**Cutover procedure on pass:**
```bash
# homelab/.env
MODEL=hammerstein-7b-v027-2

# Restart bot daemon
# Drop ping in state/pings/inbox.md (cross-machine; orchestrator picks it up)
# Write verdict memo at docs/handoffs/v0.2.7.2-shipped-or-bailed-2026-05-26.md
```

**If criteria 2 fails (tool-use STILL doesn't pass after the XML rewrite):** that's a more fundamental issue — surface back to the orchestrator before any further iteration. Could mean the trainer's chat template is over-rendering XML escapes, the model has format priors from upstream Qwen that resist re-training, or something else structural.

**Fallback:** if v0.2.7.2 fails any preservation gate, revert to `MODEL=hammerstein-7b-v026-2` (still the validated regression floor). v0.2.7.1 is NOT a safe fallback — it has the self-state win but the tool-use regression, which is exactly what we're trying to fix.

## Answers to PC's 5 open questions (orchestrator side)

1. **Extraction high-signal soft-miss:** noise. Don't dedicate training axis to it. Relaxed in the v0.2.7.2 gate from ≥95% to ≥90% to accommodate.
2. **Tool-use judgment:** rewrite pairs (primary v0.2.7.2 fix). Real fix not bot-side workaround. Model emits native format; bot stays single-format.
3. **ml-09 leak:** defer. 95% acceptable for ship.
4. **ex-10 pure-question:** spec is right. Add 3-5 explicit discrimination pairs in v0.2.7.2 (secondary fix above).
5. **Continued-from-continued discipline:** continue stacking through v0.2.7.x; **plan a clean-rebase from v0.2.6.2 base + accumulated additions JSONLs (concat all of v0.2.7.x + v0.2.7.1.x + v0.2.7.2.x at single-pass) BEFORE v0.2.8 starts.** Reset gives cleaner provenance + likely better convergence than the stacked-continued path. Don't reset now (throws away v0.2.7.x gains). File a `hm-013` task: "v0.2.8 prep — clean-rebase from v0.2.6.2 base + accumulated v0.2.7.x additions, single-pass concat" so it doesn't get lost.
