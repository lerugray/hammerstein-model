**tu-05 (no-search-when-knowledge-suffices):** PASS — model answers from training knowledge, no tool call.

### Diagnostic hypothesis

The XML rewrite likely got mistraining via the chat template. The training pairs embedded `<tool_call>...</tool_call>` in assistant `content`. But Qwen's chat template (which Modelfile.v027_2 includes) ALSO outputs `<tool_call>` tags when `.ToolCalls` is non-empty. So during training, the tokenizer may have seen the literal `<tool_call>` text as a normal token sequence rather than as the structured tool-call slot the inference-time template uses.

Either:
- The model now thinks `<tool_call>...</tool_call>` is something to OUTPUT WHEN ASKED, not something to USE TO CALL TOOLS
- The model confuses "Checking. + tool_call XML" with "say Checking. then refuse"
- Some other structural mismatch between training-time and inference-time tool-call rendering

The fact that tu-05 (definition-from-knowledge) still works suggests the voice/knowledge axes are preserved; only tool-INVOCATION is broken.

Model emits `[]` on every high-signal extraction probe:

```
ex-01 (routing-decision):    [] []
ex-02 (project-status):      [] []
ex-03 (workflow-pref):       [] []
ex-04 (strategic-fact):      [] [P]   (1/2)
ex-05 (voice-coded):         [] []
ex-06 (operational-decision):[] []
```

The 5 v0.2.7.2-pure-question-extraction-edges pairs (all `[]` outputs) at 10x oversample = 50 examples saying "emit []". Combined with v0.2.7.1's low-signal-extraction-edges (8 × 10x = 80) and v0.2.6.x's extraction carryover (10×9 + 12×9 = 198), there are now ~330 examples saying "emit `[]`" against ~30 examples in v0.2.7-canonical-positives saying "emit structured non-empty". The empty-array reflex won the gradient war.

Fixable in v0.2.7.3 by:
- Adding 10-15 high-signal extraction reinforcement pairs at high oversample
- OR reducing oversample on the low-signal/pure-question files

But this is a v0.2.7.3 question, not a v0.2.7.2 ship question. v0.2.7.2 ships nothing.
