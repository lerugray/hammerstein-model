## Iteration approach + diminishing returns

Three iterations tonight (v026 → v026.1 → v026.2). Each one traded
one axis for another. By v0.2.6.2 the failure-mode budget had stabilized:
voice + empathy + extraction net positive, V2 register + self-state
slightly negative. The targeted-data-add approach is bouncing around
the local minimum, not converging.

The remaining issues need data-design thinking, not more single-axis
pair adding:
- **Meta-leakage** ("training context", "no persistence", "shut down
  immediately after this message") — likely needs system-prompt redesign
  or chat-template separation between deployment-facts context and
  conversational context
- **Audit/casual register confusion** — possibly needs a register-
  classifier rethink or stronger casual-tone-on-framework-topic pairs
- **Low-signal `[]` extraction** — needs either much heavier oversample
  (8-10x not 5x) OR a separate fine-tune for extraction specifically
  (low-signal vs high-signal are different tasks)

Ray's call: ship v0.2.6.2 now (reversible via env var bump), log
real-world failure cases over the next 24-48 hours of daily use, then
do a deep data-design pass for v0.2.7 with actual usage data instead
of synthetic eval prompts.

## Next-session work to consider (v0.2.7 data-design pass)

Not for tonight; flagging for whenever the next major iteration starts:

1. **Meta-leakage architecture** — the model has gotten meta-aware in
   a leaky way (talks about its training, its base model, its
   persistence model in prose). Consider:
   - Separate the deployment-facts SYSTEM block from the conversational
     SYSTEM block — only inject deployment facts when the question asks
     about deployment
   - Add explicit anti-pairs showing what NOT to do (response includes
     "training data" / "base model" / "this model" → REJECTED shape)

2. **V2 register classifier** — model bounces audit/casual on knowledge
   prompts. Possible fix: tag training pairs explicitly with intended
   register and add a register-stability axis to the auto-grader.

3. **Extraction as separate fine-tune** — high-signal extraction works
   100%; low-signal `[]` at 50% suggests the two are different tasks
   getting mixed in the same weight updates. Consider a separate
   extraction-only fine-tune step or a much higher oversample (8-10x)
   on the low-signal subset.

4. **Real-usage failure log** — instead of more synthetic eval prompts,
   pipe production responses that Ray finds wrong-shaped into a
   `data/v027-real-failures.jsonl` over the next week. Train against
   actual misses.

5. **Tool-call routing** — v1-05 Napoleon III in v0.2.6.1 emitted a
   real `<tool_call>web_search` instead of refusing; v0.2.6.2 went back
   to refusing. The right behavior depends on whether tools are wired
   up at inference time. Worth aligning the SFT data with what the
   sidecar actually offers in production.
